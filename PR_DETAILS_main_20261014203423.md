## 📝 Resumen Ejecutivo

Este PR refina significativamente la metodología del benchmark de observabilidad, pasando a medir el overhead de CPU/memoria sobre ventanas temporales dinámicas y específicas para cada escenario. Además, se añade una guía completa para el despliegue en Google Cloud Platform y un script para automatizar la captura de evidencias del pipeline de telemetría.

### 🚀 **Punto de Entrada para Review:**
**Comenzar por:** `benchmark/analyze_overhead.py` - Se modificó la lógica central para la consulta y análisis de métricas de Prometheus, impactando directamente la fiabilidad de los resultados del benchmark.

### 🔧 Cambios Implementados:
-   **Refactorización de la lógica de análisis:** Ajustes en `benchmark/analyze_overhead.py` para usar consultas Prometheus de rango y agregación de métricas en Python, permitiendo análisis más precisos por ventana temporal.
-   **Automatización del benchmark:** `scripts/run-benchmark.sh` ahora registra ventanas de tiempo exactas para cada escenario y maneja umbrales de k6 de forma no-bloqueante.
-   **Documentación de despliegue en GCP:** Nueva guía paso a paso para desplegar todo el stack en Google Cloud Platform (`docs/despliegue-gcp.md`).
-   **Script de captura de evidencias:** Nueva herramienta `scripts/capturar-evidencias.sh` para generar automáticamente screenshots del estado del pipeline (Jaeger, Grafana, Prometheus).
-   **Configuración de k6:** Umbrales más flexibles y desactivación de la salida JSON raw para optimizar las corridas.

### [📁 Configuración k6] [🔄 Modificado] `benchmark/load.js`

**📍 Ruta:** `benchmark/load.js`

**🔍 Cambio:** Los umbrales de latencia para `http_req_duration` se han flexibilizado y `abortOnFail` se ha establecido explícitamente a `false`. Esto permite que el benchmark complete sus corridas aunque se superen los SLOs definidos, asegurando la comparabilidad entre escenarios.

```javascript
  thresholds: {
    http_req_duration: [
      { threshold: 'p(95)<2000', abortOnFail: false },
      { threshold: 'p(99)<3500', abortOnFail: false },
    ],
    // ...
  },
```

### [📁 Configuración Docker] [🔄 Modificado] `docker-compose.yaml`

**📍 Ruta:** `docker-compose.yaml`

**🔍 Cambio:** Se eliminó la variable de entorno `K6_OUT` para el servicio `k6`. Esta optimización evita la generación de archivos JSON masivos con cada muestra individual, ya que el resumen agregado es suficiente para el análisis y mejora el rendimiento de la prueba.

```yaml
    # Sin K6_OUT: volcar cada muestra individual a JSON genera ~100 MB por
    # corrida y la escritura compite con la propia prueba. El handleSummary de
    # load.js ya produce el resumen agregado que consume analyze_overhead.py.
```
